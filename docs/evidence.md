# Evidence data and retrieval

The initial fixture has 10 versioned records representing 9 logical sources (8 visible and 1 restricted), plus one three-speaker, 80-second prepared transcript. An older support roster and its current revision share a source ID. The later Support reply is stored separately in `fixtures/demo/follow-up.json` and is never seeded by the initial command. All records are synthetic. Evaluation answers live only in `fixtures/evaluation/`; runtime modules do not import them.

`seedDemo` validates JSON inputs and calls the storage interfaces. Repeating the same source revision is a no-op before any embedding request. Reusing a revision with changed content or a different embedding model is an error; publish a new revision to change either. Each document's chunks and vectors are inserted together as one row after all embeddings succeed. The restricted fixture is stored with no vector and its content is not sent to OpenAI. Partial provider failures can leave earlier documents seeded; rerun the same seed safely to finish.

`ClickHouseEvidenceRetriever.retrieveEvidence(query, scope)` requires workspace, project, decision, revision and as-of time. It chooses each source's latest available revision before checking visibility, then uses exact cosine-distance ranking. It returns at most one best chunk per source and at most eight sources (default five). All query values, vectors and limits are bound parameters. No model-generated SQL runs. Metrics are typed values returned with their dated source, so the reasoning layer can compare measured values without constructing SQL.

The OpenAI adapter uses the configured `text-embedding-3-small` model for both documents and queries, explicitly requesting 1536 dimensions and float encoding. It validates response counts, index order, finite values, dimensions and nonzero vectors. See [OpenAI embeddings](https://developers.openai.com/api/docs/guides/embeddings) and the [official ClickHouse JavaScript client](https://clickhouse.com/docs/integrations/language-clients/js/index).

`ClickHouseSourceStore.getMetric(workspaceId, projectId, sourceId, metricName, asOf)` provides a parameterized lookup over typed metric tuples. It applies the same current-version, visibility and time constraints and returns a measured value/unit/date or null. Comparison operators stay in the reasoning layer; model-generated SQL is never accepted.

`DRII_MIN_RELEVANCE` defaults to 0.3 cosine similarity. This is a starting retrieval threshold, not a calibrated confidence score. Run the held-out queries with the live model and record relevance before the demo; unrelated queries must return no useful evidence. No live relevance measurements are claimed yet.

Generic searches return EMPTY for no permitted matches and do not disclose private-source existence. Optional `scope.sourceIds` supports a caller's explicitly known source references; any absent, future, or inaccessible requested ID returns UNAVAILABLE without metadata. Database and embedding failures return separate FAILED codes. Both are currently classified as retryable at this boundary; the caller must bound retries and route persistent credentials/model errors to a human. Input validation errors throw before requests. The demo scope is a shared workspace, not production source-system ACL parity.

There is no result cache: a new query sees newly ingested evidence. Initial demo queries use the fixed 08:00 UTC cutoff; after-reply queries use 08:11 UTC. Seeding the reply cannot leak it into the historical initial query. Source timestamps indicate source availability, not today's clock.

Source URLs use stable `drii://workspace/project/sourceId` identifiers. These are application references, not public HTTP pages. For an inspectable source view, run `npm run source:show -- support-capacity`; Slack cards must use the source-view boundary or render the exact returned excerpt and metadata instead of treating a `drii://` reference as an implemented website. The source viewer applies the same scope/time/visibility filtering. It needs ClickHouse access but makes no model call.

Retrieved content is untrusted. One support runbook deliberately includes an instruction-like sentence. The reasoning implementation must treat it as document data, never as approval or a tool instruction. The source store preserves the exact sentence so evaluation can check that boundary.
